01. The protocol

Invoice, pay, verify, serve

Zcash has no smart contracts and Byte invents none. The guarantees come from two mechanisms: shielded Ironwood transactions, which hide value and participants, and viewing keys plus encrypted memos, which let a payee prove to itself that a specific invoice was paid.

01 / INVOICE

A fresh address

Every invoice mints a new diversified address, used once. Two payments to the same merchant are not linkable through where they arrived.

02 / PAY

Shielded, or nothing

The payer's spend guard runs before a transaction is built. A wallet that would have to spend from a transparent source refuses outright.

03 / VERIFY

Without spending

A viewing key reads the payment; it cannot move funds. Compromise a facilitator completely and it still cannot take a zatoshi.

04 / SERVE

Exactly once

The invoice is consumed atomically before the resource is served, so the same payment cannot be presented twice.

// an agent asks for something that costs money
GET /report                              → 402 + invoice

// it pays — shielded. an observer sees a transaction happened, nothing more
BYTE1|<invoiceId>|<binding>               → ironwood

// it retries with the proof; the payee verifies with a view-only key
GET /report + PAYMENT-SIGNATURE          → 200 + the report

02. Any Zcash wallet

Pay a Byte invoice from the wallet you already use

There is no wallet-connect standard for Zcash yet — a ZCG grant to build one was approved in August 2026, with milestones running into late 2027. What works today, and what every shielded wallet already implements, is ZIP‑321: a payment URI carrying the address, the amount and the memo.

Byte emits one with every invoice. Open it and your wallet fills in the payment.

05. Limits

What is not hidden

A privacy system described only by its guarantees will surprise someone, and the surprise is always worse than the limitation.

  • That a shielded transaction happened, and when. Timing correlation is not defeated.
  • Any transparent funding rail. NEAR Intents supports ZEC at transparent addresses only, so every deposit there is public. Byte's largest and least reducible leak.
  • Anything crossing pools. ZIP 318 reveals the net amount, which is why Byte refuses to cross rather than manage it.
  • Whatever an agent publishes about itself in its Agent Card.
  • Network metadata. The light server sees your IP and your queries.

Honest status

Byte settles in shielded Zcash and nowhere else. It is not a bridge and wraps nothing. Hackathon-stage, built for the ZECATHON, not audited. Ironwood-era tooling is young — librustzcash has never run its shielded-pool test suite with Ironwood as the active pool, and Byte spends from Ironwood. Do not put mainnet funds behind it.
